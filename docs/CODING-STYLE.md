## 1. ドキュメントコメント規約

**コメントを書くべきかどうかの判断は、この規約の対象外。** 書くと決めたコメントの
「形」だけを定める。この規約があることは、コメントを増やす理由にはならない。

1. **5行を超えるコメントは単一段落で書かない。** `WHAT` / `WHY` / `RESOLVED` /
   `NOT RESOLVED` のような見出しで分割する。見出し名は内容に合わせてよいが、
   「何をするか」と「なぜそうしたか」は必ず分ける。
2. **4項目以上の列挙は散文に埋め込まず、箇条書きにする。** 3項目以下なら散文でよい。
3. **外部ドキュメント参照は1コメントにつき2箇所まで。** 3箇所以上必要なら、
   コメント冒頭に `Design: docs/DESIGN.md §3.5` の形でまとめて列挙する。
4. **一文が40語を超えたら分割を検討する。** 日本語なら読点で3回以上つないだ文が目安。

### 見出し分割の例

```pascal
{
  TPMLAudioStream — 入出力スペックが異なる場合に変換を挟むストリーム。

  WHAT:
    リサンプルとチャネル変換を行い、アプリが任意のスペックで書き込めるようにする。

  WHY:
    デバイス側のスペックを固定するとアプリに変換責務が漏れるため。

  RESOLVED:
    - 破棄時に自動で unbind する
    - Lock / Unlock はコールバック実行中の排他に限る

  NOT RESOLVED:
    - コールバック中の例外の遮断方法 (Design: docs/DESIGN.md §5.4)
}
```

## 2. ファイルヘッダ

書式は `docs/DESIGN.md` §1.4 に従う。`Origin:` 行は機械可読で、`tools/checkorigin` が
DESIGN.md 第11章の由来列との一致を CI で検査する。

- 移植 / 一部移植: `Origin : ported from SDL (元ファイル名)` ＋ zlib 告知 ＋ SDL の著作権表示
- クリーンルーム: `Origin : original work (clean-room design; not derived from SDL sources)`

**ヘッダの `Origin:` / `Scope:` / `Design:` 行は、上記規則3の「1コメントにつき2箇所まで」に
数えない。** これらはまさに「冒頭にまとめて列挙した」形そのものである。

## 3. 移植コード固有の規約

`docs/DESIGN.md` §8.7 の要点。移植担当は以下を機械的に適用する。

- **`PORT-NOTE:`** — C 側の関数名、意図的に変えた振る舞い、疑わしい元コードの箇所を記す。
  `PORT-NOTE(bug):` は元コードのバグを直した箇所。`docs/UPSTREAM-NOTES.md` に集約する。
- **`#ifdef` は消す。** Linux 内の分岐は実行時の `dlopen` 成否に置き換える。
- **4つの機械的変換**: `goto` → `try/finally`、`void *` → 具象型、`(cast)` → 派生クラスの
  フィールド参照、`static` グローバル → 所有者オブジェクトのフィールド。
- SIMD 部分は移植せず、スカラー版だけ移植する。

**C コードを無検証で写してはならない。**「同じロジックか」ではなく「意図した振る舞いか」を
確認する。実例として `SDL_ibus.c` 115 行目には、引数を上書きしてから自分自身と比較している
ため型名検証が常に成功するバグがある。

---

## 4. 命名

`docs/DESIGN.md` 第8章に従う。接頭辞は `TPML`（クラス）/ `IPML`（インターフェース）/
`EPML`（例外）。SDL 互換の `TSDL` 接頭辞は使わない。
