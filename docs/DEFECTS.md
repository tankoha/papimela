## A. papimela 自身の実装不具合（すべて修正済み）

### D-01 外部データシンボルの宣言に `cdecl` を付けてコンパイル不可
- **発見**: 2026-09-28 14:2x（spike1 の初回ビルド）
- **症状**: `Syntax error, ":" expected but ";" found`
- **原因**: FPC は変数宣言に `cdecl` を許さない。関数宣言の構文をそのまま流用していた
- **対応**: `var X: T; external LIB name 'X';`（`cdecl` なし）に修正
- **状態**: 修正済み（T-01）

### D-02 fcitx5 に対して `Controller1.Activate()` を呼ばず、キーが一切消費されない
- **発見**: 2026-09-28 14:3x（spike2 の初回実行）
- **症状**: `ProcessKeyEvent` が常に `false` を返し、変換中テキストが 0 回。4 項目 FAIL
- **原因**: 2 つ重なっていた。(1) fcitx5 は既定で「非アクティブ」状態（`keyboard-us` 担当）で始まるため `Controller1.Activate()` が必要。(2) `SetCurrentIM` はフォーカス中のコンテキストに作用するので `FocusIn` より先に呼んでも効かない
- **対応**: `FocusIn` → `Activate` → `SetCurrentIM` の順序に修正。この知見は `PaPiMeLa.TextInput.Fcitx` の `Activate` にコメントとして残し、設計書にも反映
- **状態**: 修正済み（T-02、T-03）
- **備考**: 実装の不具合ではなく**プロトコル理解の誤り**。スパイクを先に書いた価値が出た箇所

### D-03 `Pointer` から手続き変数型への暗黙変換ができずコンパイル不可
- **発見**: 2026-09-28 21:2x（`Platform.DBus` の初回ビルド）
- **症状**: `Incompatible types: got "Pointer" expected "<procedure variable type>"` が 32 件
- **原因**: objfpc モードでは `GetProcedureAddress` の戻り値を関数ポインタへ直接代入できない
- **対応**: untyped `out` 引数を取る `Bind` ヘルパを導入し、`Pointer(ATarget) := ...` で代入。30 箇所の個別キャストを回避
- **状態**: 修正済み（C-01）

### D-04 `TArray<String>` が objfpc モードで使えない
- **発見**: 2026-09-28 21:5x（`Events` の初回ビルド）
- **症状**: `Generics without specialization cannot be used as a type for a variable`
- **原因**: `TArray<T>` は Delphi モードの構文。設計書はこの型名で書かれていた
- **対応**: `TPMLStringArray = array of String` を `Types` に定義。設計書 §8.5「公開 API に `specialize` 構文を露出しない」にもむしろ沿う形になった
- **状態**: 修正済み（C-01）

### D-05 `clock_gettime` / `CLOCK_MONOTONIC` が RTL から公開されていない

- **対応**: libc へ直接束縛（`external 'c' name 'clock_gettime'`）し、`CLOCK_MONOTONIC = 1` を自前定義

### D-21 シートのリスナーを付ける前に capabilities が配送され、キーボードを取り出せない
- **発見**: 2026-09-29（`test/demo_japanese_input` を 5 秒動かしたら「キーマップ受信: False」だった）
- **症状**: `wl_seat` は束縛できているのにキーボードが一切動かない。`wl_keyboard.keymap` も
  `enter` も届かない
- **原因**: `TPMLWaylandConnection.Connect` がレジストリの roundtrip を 2 回行う間に
  `wl_seat.capabilities` が配送される。シートのリスナーを付けていたのはその**後**なので、
  capabilities を取りこぼし、`wl_seat_get_keyboard` を呼ぶ機会が無かった。
  **束縛とリスナー登録の間に dispatch を挟んではいけない**という Wayland の基本を外していた
- **対応**: 接続に `OnSeatBound` コールバックを追加し、レジストリハンドラが `wl_seat` を
  束縛した瞬間にシートオブジェクト（＝リスナー）を生成するようにした。ビデオバックエンドは
  `Connect` の前にこのコールバックを設定する
- **状態**: 修正済み（修正後は「キーマップ受信: True / フォーカス取得: True」）
- **教訓**: 静的解析もコンパイラも捕まえられない種類の不具合。**実際に動かしたから見つかった**。
  合成キーによる自動テスト（T-06）も通っていたので、対話デモを書かなければ残っていた


### D-22 ウィンドウのフォーカス変化が IME に伝わっていない
- **発見**: 2026-09-29（利用者が `test/demo_japanese_input` を実際に操作した出力から。
  「キーボードフォーカスを喪失 → 取得」が記録されているのに、IME 側へ何も送っていなかった）
- **症状**: 別のウィンドウへ移っても fcitx5 はこちらの入力コンテキストを注目したままになる。
  2 つのクライアントが同時に IME フォーカスを持つ状態になり、変換中テキストや

- **原因**: `TPMLKeyboardState.SendFocus` は `WindowFocusGained` / `Lost` をキューへ積むだけで、

  `TPMLTextInputSystem` はセッションのウィンドウと一致する変化だけを
  `Activate` / `Deactivate` へ中継する。`Start` / `Stop` と二重にならないよう
  `FFocused` で遷移のときだけ通す
- **状態**: 修正済み（実機検証 2026-09-29。T-07 を参照）
- **教訓**: 単一ウィンドウのデモでは症状が出にくい。**利用者が実際に触って別ウィンドウへ
  移ったログ**から見つかった。自動テストも対話デモも単一アプリしか見ていなかった

### D-23 サーフェスが解決できないときフォーカス喪失を取り落とす
- **発見**: 2026-09-29（D-22 の修正を実機で確かめる直前のコード読み）
- **症状**: `wl_keyboard.leave` で `user_data` からウィンドウ ID を引けなかった場合、
  `SendFocus(..., False)` を呼ばずに終わる。D-22 と同じ「IME がフォーカスを持ったまま」の
  状態が、別の入口から再現する
- **原因**: `HandleKeyLeave` が `WindowIDOf(ASurface)` の結果が 0 でないことを通知の条件に
  していた。サーフェスは `leave` の時点で既に破棄されていることがあり、そのとき 0 になる
- **対応**: 解決できなければ直前に保持していた `FKeyFocus` を使う。`FKeyFocus` は
  条件付きではなく必ず 0 に戻す。`leave` は「失った」という事実そのものなので、
  誰が失ったか分からなくても通知を落としてはいけない
- **状態**: 修正済み（実機検証 2026-09-29。別ウィンドウへの往復 4 回すべてで
  `フォーカスを喪失` と `取得` が対になって記録された）
- **教訓**: D-22 の修正で経路を作ったが、その経路に**通らない条件**が残っていた。
  修正が「送るようにした」で終わっていないか、送らない分岐が残っていないかを見る

### D-24 configure がウィンドウフラグ集合を丸ごと置き換え、生成時の指定が消えていた
- **発見**: 2026-09-29（pointer-constraints の実装中。`MouseGrab := True` のあと
  `TPMLWindowFlag.MouseGrabbed in Win.Flags` が False になり、テストが落ちた）
- **症状**: 最初の `xdg_toplevel.configure` が届いた時点で、`Resizable` や
  `Borderless`、`HighPixelDensity`、`MouseGrabbed` が `Flags` から消える。
  ウィンドウ自体は正しく振る舞う（バックエンドは生成時に設定済み）が、
  **アプリが `Flags` を見ると嘘の値が返る**
- **原因**: `TPMLWindow.ApplyFlags` が `FFlags := AFlags;` と集合を置き換えていた。
  バックエンドが報告するのは自分が知っている 3 つ（Maximized / Fullscreen /
  InputFocus）だけなので、それ以外は毎回消えていた
- **対応**: フラグごとに持ち主を決め、バックエンドが持つ集合だけを差し替える。
  `FFlags := (FFlags - BackendOwned) + (AFlags * BackendOwned)`。境界は定数
  `BackendOwned` としてコードに書き、「コンポジタしか知らないフラグ」と明示した
- **状態**: 修正済み（`test_pointer_constraints` が「configure のあとも生成時の
  Resizable が残る」を検査する）
- **教訓**: 新機能を足したときに**既存の嘘が露出した**類。`MouseGrabbed` を
  `Flags` に載せようとして初めて、同じ場所を通る `Resizable` も壊れていたと分かった。
  状態を 2 箇所が書くなら、どちらが持ち主かを型か定数で表に出す

### D-25 FPC の `Format` は `+` フラグを解釈しない
- **発見**: 2026-09-29（T-09 の出力が `rel=(313.1f, 313.1f)` になっていた）
- **症状**: `Format('rel=(%+.1f, %+.1f)', [X, Y])` が数値を出さず、`.1f` を文字として
  出力する。**表示される値が嘘になる**ので、デモの相対移動量は最初から読めていなかった
- **原因**: FPC の `Format` が受け付ける書式は `%[index:][-][width][.prec][type]` で、
  C の `printf` にある `+`（符号を必ず付ける）は含まれない。`%+` に当たると
  書式指定の解析が途中で止まる
- **実測**: `Format('(%+.1f)', [Single(1.25)])` → `(.1f)`。`%.1f` と `%6.1f` は正常
- **対応**: `+` を外して `%.1f` にした。負数には最初から `-` が付くので実害は無い
- **状態**: 修正済み
- **教訓**: C の書式をそのまま持ち込まない。**出力が壊れていることに気づけたのは、
  値が座標と一致しない（`rel` に `abs` の Y が出ていた）と分かったから**であって、
  形式だけ見ていたら見落としていた

### D-26 デモが絶対移動をすべて相対移動として数えていた

### D-27 デモが小文字のキーシムしか受けず、Shift 付きで押すと無反応
- **発見**: 2026-09-29（T-09 の再実行。`（割り当ての無いキー keysym=$47）` が延々と出ていた）

- **状態**: 修正済み
- **教訓**: 指示の書き方が操作を誘導する。**大文字で書いたら大文字で押される。**
  診断行（割り当ての無いキーの keysym 出力）を入れておいたおかげで即座に分かった

### D-31 ピクセル形式のマスク導出と色変換に 2 つの誤りがあり、往復検査で検出した
- **発見**: 2026-09-29（`test_pixels` の初回実行）
- **症状**:
  - RGB565 / BGR565 / RGB332 のマスクが 1 成分ずれる（R に G の幅が付く）
  - 8 ビット成分の形式で色 → 画素値 → 色 の往復がゼロ除算で落ちる
- **原因**:
  - **3 成分のレイアウト**（332 / 565）には X の枠が無いのに、4 成分と同じ
    位置合わせをしていた。`XRGB` + `565` は「X(5), R(6), G(5), B(0)」ではなく
    「R(5), G(6), B(5)」である

- **対応**: レイアウトごとの成分数を表に持ち、3 成分なら並びから X を抜いて詰める。

- **状態**: 修正済み（`test_pixels` が 13 形式のマスク比較と 12 形式 x 6 色の

- **教訓**: どちらも**実装を読んだだけでは気づかなかった**。SDL の 240 行の
  switch を算出に置き換えた以上、**表を写していない分の正しさは検査で担保するしかない**。
  往復検査は 1 ビットのずれでも必ず値が変わるので、この種の置き換えと相性が良い

### D-40 CI だけで GLES2 の検査が止まる（FPC が浮動小数点の例外を有効にしている）
- **発見**: 2026-10-01（GPU のドライバの比較を CI に入れたら、何も出力しないまま 4 時間半止まり、手で取り消した）
- **症状**: Ubuntu 24.04（Mesa 25.2.8、LLVM 20）の llvmpipe で、GLES2 のドライバのオフスクリーンの初期化が返ってこない。手元（Ubuntu 26.04、Mesa 26.0.8、LLVM 21）では `/dev/dri` を隠しても再現しなかった
- **切り分け**: (1) CI に時間制限と Mesa の EGL の記録を入れ、`eglInitialize` は済んで、その後で止まることを確かめた。(2) Ubuntu 公式の 24.04 の最小 rootfs を bwrap で動かし、CI と同じパッケージを入れて**手元で再現**した。(3) EGL を一歩ずつ呼ぶ確認プログラムが、コンテキストの作成で `EInvalidOp: Invalid floating point operation` を出して落ちた。浮動小数点の例外を無効にすると通った

- **状態**: 修正済み（T-22）
- **教訓**: **CI の手順には必ず時間制限を付ける**（既定は 6 時間）。FPC のプログラムが C のライブラリを呼ぶときは、浮動小数点の例外の設定を最初に疑う

- **症状**: `setitimer(AWhich: LongInt; const ANew: TITimerVal; AOld: Pointer); cdecl; external 'c'` と宣言して呼ぶと、C の側には `setitimer(ITIMER_REAL, NULL, NULL)` が届き、タイマーが動かなかった。眠りが一度も割り込まれないので、「割り込まれても眠り切る」の検査は**何も確かめないまま通っていた**
- **原因**: FPC は cdecl の `const` の record を C の値渡しとして扱う。C の `setitimer` は構造体へのポインタを取るので、引数の位置がずれる
- **対応**: ポインタ型（`PITimerVal`）で宣言し、`@T` を渡す。直した後はシグナルが 31 回届き、EINTR で寝直さない実装を入れると落ちることを `-B` で確かめた
- **状態**: 修正済み（T-24。製品のコードではなく検査の誤り。コミット前に見つかった）
- **教訓**: C の関数へ構造体を渡すときは、`const` ではなくポインタで宣言する。「環境が無ければ飛ばす」と同じく、**仕掛けが本当に効いたか（シグナルが何回届いたか）を検査に数えさせる**と、この種の空振りが表に出る

### D-46 確定・周辺削除の直後に送り直す周辺テキストが、アプリが取り込む前の古い内容だった
- **発見**: 2026-10-06（#49 text-input-v3 の設計中。プロトコルの done の手順「確定を入れてから送る周辺テキストを計算する」を読み、papimela の送り直しの時機と合わないことに気づいた）
- **症状**: `TPMLTextInputSystem.TextCommitted` が、確定を `TextInput` としてキューへ積んだ直後に `GetSurroundingText` を呼んで IME へ送っていた。アプリはまだ `Poll` していないので、届くのは**確定を入れる前のバッファ**。周辺削除（`DeleteSurroundingRequested`）の後は送り直し自体をしていなかった。IME は古い周辺テキストを持ったまま次の変換をするので、再変換や周辺削除の位置がずれうる（Fcitx の経路でも同じ）
- **原因**: コメントに「ここでの再送は次の Pump 以降に効く」と書いていたが、実際はその場で取り直していた。取り直す時機（アプリが取り込んだ後）と送る時機を区別していなかった
- **対応**: 確定・周辺削除の通知では印（`FResendRequested`）だけを立て、その Pump の終わりに `FResendArmed` へ移し、**次の Pump の始め**に取り直して送る。間にアプリの `Poll` が入る。T-27 の 11 節が「確定を流した Pump の中では送らない」「次の Pump で取り込んだ後のテキストを送る」「1 回だけ」を見る。直す前のコードで 2 件落ちることを確かめた
- **状態**: 修正済み（T-27。Fcitx の経路は T-07 / T-11 の再実行で退行が無いことを確認）
- **教訓**: 「通知を積む」と「アプリがそれを処理し終える」の間には Pump の境目がある。アプリの状態を読み直す処理は、通知と同じ Pump の中に置かない。D-39 / D-43（積んだ時と実行する時の間）と同じ形の、時機の取り違え

### D-47 IME が押すほうを消費したキーの、離すほうの KeyUp がアプリへ出ていた
- **発見**: 2026-10-06（#48 の下調べ。スパイク 3 で ibus-mozc が「離す」を一度も消費しないことを見て、papimela の経路を読んだ。fcitx5-mozc でも同じだった）
- **症状**: 変換中のローマ字のように IME が押すほうを消費したキーは KeyDown を出さないが、離すほうは IME が素通しにするので KeyUp だけがアプリへ出る。T-06 の 14 キーで、KeyDown 0 件に対して KeyUp 14 件だった
- **原因**: `TPMLKeyboardState.SendKey` が、押すのと離すのを別々に IME の結果だけで決めていた。IME は押すと離すを対にして消費するとは限らない
- **対応**: KeyUp は「KeyDown をアプリへ出したキー」にだけ出す（`FEmittedDown`）。逆に KeyDown を出した後で離すほうが消費されても KeyUp は出す（押したまま残さない）。フォーカスを失ったときの一斉解放も同じ規則。T-06 に「KeyDown を出さなかったキーの KeyUp も出さない」を足し、直す前の規則で 14 件出て落ちることを確かめた。T-29 が返信待ちの経路でも見る
- **状態**: 修正済み（T-06、T-29）
- **教訓**: 外部の部品（IME）が対になった入力を対のまま扱うと決めつけない。合成キーの検査（T-06）はスキャンコードを付けていなかったので、この規則が働く道を通っていなかった。検査の入力は実物（シート）と同じ形にする

### D-48 カーソルに接していない周辺削除の要求で、頼まれていない文字まで消していた（Fcitx）
- **発見**: 2026-10-06（#48 で IBus と Fcitx の周辺削除の換算を 1 つの関数にまとめる途中、境目の値を検査に書いていて気づいた。実機では起きていない）
- **症状**: IME の要求は「カーソルから offset 文字の位置から n 文字」で、papimela のモデルは「カーソルの前 / 後ろを消す」。範囲がカーソルに接していないとき（例: カーソル 3 で「先頭の 1 文字だけ」= (-3, 1)）、カーソルからその端までを丸ごと消す換算になっていた（例では 3 文字）。範囲が先頭より前で終わる場合も、先頭で切り詰めた後の空の範囲をカーソルの前 1 文字として消していた
- **原因**: `TPMLFcitxTextInputBackend.HandleDeleteSurrounding` が、範囲の始まりと終わりをカーソルとの差だけで前後に振り分けていた。範囲がカーソルに接しているかを見ていなかった
- **対応**: 換算を `PMLDeleteSurroundingFromChars`（`PaPiMeLa.TextInput.Backend`）にまとめ、IBus と Fcitx で共有した。範囲がカーソルに接していなければ何も消さない（頼まれていない文字を消すよりよい）。先頭より前・末尾より後ろにはみ出す分は切り捨てる。T-30 に境目の 7 件を足し、接していない範囲を消す換算に戻すと 3 件落ちることを確かめた
- **状態**: 修正済み（T-30）
- **教訓**: 表せない要求は、近いものに丸めずに断る。丸めると利用者の文字が消える

### D-44 合成の丸めを「SDL の MULT_DIV_255 と同じ狙い」と書いていたが、SDL は切り捨てだった
- **発見**: 2026-10-02（論理解像度の実装を SDL の実物と画素で比べたら、半透明の場面だけ色が 1 違った。SDL は `0x9f`、papimela は `0xa0`）
- **箇所**: `src/PaPiMeLa.Surface.Blit.pas` の `Mul255` のコメント（#29 で書いた）
- **症状**: コメントは SDL と同じ丸めであるかのように読めるが、実際は違う。背景 (0, 0, 64) に白をアルファ 128 で重ねると、B は厳密には 159.87。SDL は 64×127/255 = 31.87 を 31 に切り捨てて 159、papimela は 32 に四捨五入して 160
- **原因**: SDL の `MULT_DIV_255`（`video/SDL_blit.h`。`+1` してからシフトする）を、papimela の `+128` してからシフトする式と同じ種類のものと思い込んで書いた。**全 65,536 組で計算すると、SDL の式は切り捨てと、papimela の式は四捨五入と全件一致する**。SDL のソフトウェアレンダラの塗り（`render/software/SDL_draw.h` の `DRAW_MUL` = `a * b / 255`）も切り捨て
- **対応**: コメントを事実に合わせて直した（`PORT-NOTE`）。**計算そのものは変えていない**。四捨五入は厳密な値に近く、GLES2 のドライバ（GL は色を書くときに最も近い値へ丸める）とも揃いやすい。SDL の切り捨てには揃えない（2026-10-10 に持ち主が決めた。SDL との画素の比較ではこの 1 の差を既知として扱う）
- **状態**: 訂正済み（コメント）。丸めは四捨五入のまま（2026-10-10 に決定）
- **教訓**: 「SDL と同じ」と書くときは、式の形ではなく値で確かめる。この種の式は全入力を数秒で回せる

### D-53 スワップ間隔が装置全体で 1 つしかなく、コンテキストを作るたびに 0 へ戻る
- **発見**: 2026-10-01 に Sonnet が「怪しい点」として挙げ（#33 / #39）、2026-10-10 に SDL の実物で確かめた
- **箇所**: `reference/SDL/src/video/SDL_egl.c` の `SDL_EGL_CreateContext`（`egl_swapinterval = 0`）・`SDL_EGL_SetSwapInterval`・`SDL_EGL_GetSwapInterval`、`src/video/wayland/SDL_waylandopengles.c` の `Wayland_GLES_SetSwapInterval`
- **症状**: ヘッダは `SDL_GL_SetSwapInterval` / `SDL_GL_GetSwapInterval` を「現在のコンテキストの」スワップ間隔と書いているが、値は `egl_data` に 1 つだけで、`SDL_GL_CreateContext` のたびに 0 へ戻る。窓 A とコンテキスト 1 で間隔を 1 にしてから窓 B とコンテキスト 2 を作り、A とコンテキスト 1 に戻すと:
  - **Wayland**: Get は 0 を返し、A は**実際に VSync を失う**（200 Hz の画面で 200 fps → 約 2 万 fps）。SDL はここで間隔を自前で管理し、全部の窓に同じ 1 つの値を使うため

- **実測**: システムの SDL 3.4.2（`libSDL3.so.0.4.2`。上の 3 箇所は `reference/SDL` の版と同じ中身であることを差分で確かめた）を C から呼んだ。手元の labwc（200 Hz）、radeonsi。X11 は Xwayland で `SDL_VIDEO_FORCE_EGL=1`（`EGL_PLATFORM=x11` も要る。下の補足）。`docs/TEST-LOG.md` の使い捨て検証
- **原因**: 間隔をコンテキストごとに持っていない。SDL 自身も `Wayland_GLES_SetSwapInterval` に「`FIXME: technically, this should be per-context, right?`」と残しており、作者が知っている制限
- **papimela への影響**: **同じ作りを写していた**。`TPMLEGLBackend.FSwapInterval` が 1 つで、`CreateContext` が 0 に戻していた。しかも公開 API は `TPMLGLContext.SwapInterval` と**コンテキストの性質のように見せていた**ので、SDL より誤解を招く。2026-10-10 に持ち主の判断で**コンテキストごとに直した**（`PORT-NOTE(bug)`）。間隔はコンテキストの記録に持ち、現在にするたびに描画面へ効かせる（Wayland は待ちを自前で行うので、現在のコンテキストの値で待つ）。検査は T-21 の 7.（実装より先に書き、直す前の papimela で 4 件落ちた。B の窓が約 1 万 5 千 fps、A に戻しても約 1 万 5 千 fps）
- **状態**: **未対応**。SDL 側は FIXME として既に知られているので、報告の要否は D-18 たちとは事情が違う。2026-10-10 に README の節へ載せた
- **補足（D-53 の確認中に見つけた別件）**: SDL 3.4.2 の X11 で `SDL_VIDEO_FORCE_EGL=1` にすると、`SDL_GL_LoadLibrary` の中で Mesa が X の `Display` を `wl_display` として扱って落ちる（`wl_proxy_create_wrapper` で SIGSEGV。`WAYLAND_DISPLAY` を外しても同じ。`EGL_PLATFORM=x11` を付けると通る）。3.4.2 はプラットフォームを 0 のまま `eglGetDisplay` に推測させており、`reference/SDL` の版は X11 のドライバが `EGL_PLATFORM_X11_KHR` を明示するよう変わっている（`X11_GLES_SetDefaultProfileConfig`）。参照版では直っている見込みだが、参照版は作って確かめていないので、不具合には数えない

### D-54 `SDL_CopyProperties` が、数を文字列で読んだときの置き場を写し元と写し先で共有する
- **発見**: 2026-10-10（#6 を移植していて `CopyOneProperty` を読んで気づき、SDL の実物で確かめた）

### D-55 `SDL_HINT_LOGGING` の解析が名前の先頭だけを比べ、空の値が "quiet" に一致する

### D-57 ヒントの変化の知らせが、環境変数があると前の値を誤り、変わっていないのにも呼ばれる
- **発見**: 2026-10-10（#6 の検査の期待値を SDL の実物で取っていて）
- **箇所**: `reference/SDL/src/SDL_hints.c` の `SDL_SetHintWithPriority` と `SDL_ResetHint` / `ResetHintsCallback`
- **症状**: 知らせ（`SDL_HintCallback`）の「前の値」に、効いていた値ではなく置いてあった値を渡す。同じ名前の環境変数 `env` があるとき:

- **原因**: 知らせを出すかの判断と渡す値に、`SDL_GetHint` と同じ「効いている値」ではなく `hint->value` を使っている
- **papimela への影響**: 前後の効いている値（環境変数を含む）を比べ、変わったときだけ、その 2 つを知らせる（T-45）。ログ（#5）はこの知らせで優先度を決め直すので、SDL では余計な決め直しが起きるだけで済む
- **状態**: **未対応・報告するかは検討中**（D-18 と同じ扱い。2026-10-10 に README の節へ載せた）
- **補足**: 同じファイルで、知らせの中から「次に呼ばれるはずの知らせ」を `SDL_RemoveHintCallback` すると、解放した要素を辿る（`next` を先に覚えているが、その `next` 自体が解放される）。これは読んだだけで、実物では確かめていないので不具合には数えない。papimela は知らせの並びの写しを辿る（T-45）。また、`SDL_ResetLogPriorities` はログの排他を持ったままヒントを読み、ヒントの側は自分の排他を持ったままログの知らせを呼ぶので、2 つのスレッドが逆の順で排他を取ると止まり得る。これも読んだだけで、papimela はヒントを読んでからログの排他を取る
