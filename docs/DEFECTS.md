## A. papimela 自身の実装不具合（すべて修正済み）

### D-01 外部データシンボルの宣言に `cdecl` を付けてコンパイル不可
- **発見**: 2026-09-28 14:2x（spike1 の初回ビルド）
- **症状**: `Syntax error, ":" expected but ";" found`
- **原因**: FPC は変数宣言に `cdecl` を許さない。関数宣言の構文をそのまま流用していた
- **対応**: `var X: T; external LIB name 'X';`（`cdecl` なし）に修正
- **状態**: 修正済み（T-01）

### D-02 fcitx5 に対して `Controller1.Activate()` を呼ばず、キーが一切消費されない
- **発見**: 2026-09-28 14:3x（spike2 の初回実行）
- **症状**: `ProcessKeyEvent` が常に `false` を返し、変換中テキストが 0 回。4 項目 FAIL
- **原因**: 2 つ重なっていた。(1) fcitx5 は既定で「非アクティブ」状態（`keyboard-us` 担当）で始まるため `Controller1.Activate()` が必要。(2) `SetCurrentIM` はフォーカス中のコンテキストに作用するので `FocusIn` より先に呼んでも効かない
- **対応**: `FocusIn` → `Activate` → `SetCurrentIM` の順序に修正。この知見は `PaPiMeLa.TextInput.Fcitx` の `Activate` にコメントとして残し、設計書にも反映
- **状態**: 修正済み（T-02、T-03）
- **備考**: 実装の不具合ではなく**プロトコル理解の誤り**。スパイクを先に書いた価値が出た箇所

### D-03 `Pointer` から手続き変数型への暗黙変換ができずコンパイル不可
- **発見**: 2026-09-28 21:2x（`Platform.DBus` の初回ビルド）
- **症状**: `Incompatible types: got "Pointer" expected "<procedure variable type>"` が 32 件
- **原因**: objfpc モードでは `GetProcedureAddress` の戻り値を関数ポインタへ直接代入できない
- **対応**: untyped `out` 引数を取る `Bind` ヘルパを導入し、`Pointer(ATarget) := ...` で代入。30 箇所の個別キャストを回避
- **状態**: 修正済み（C-01）

### D-04 `TArray<String>` が objfpc モードで使えない
- **発見**: 2026-09-28 21:5x（`Events` の初回ビルド）
- **症状**: `Generics without specialization cannot be used as a type for a variable`
- **原因**: `TArray<T>` は Delphi モードの構文。設計書はこの型名で書かれていた
- **対応**: `TPMLStringArray = array of String` を `Types` に定義。設計書 §8.5「公開 API に `specialize` 構文を露出しない」にもむしろ沿う形になった
- **状態**: 修正済み（C-01）

### D-05 `clock_gettime` / `CLOCK_MONOTONIC` が RTL から公開されていない
- **発見**: 2026-09-28 21:5x
- **症状**: `Identifier not found "clock_gettime"`
- **原因**: FPC 3.2.2 の `BaseUnix` / `Unix` はこれらを公開していない
- **対応**: libc へ直接束縛（`external 'c' name 'clock_gettime'`）し、`CLOCK_MONOTONIC = 1` を自前定義
- **状態**: 修正済み（C-01）

### D-06 `strict private` フィールドに同一ユニットの協調クラスから触れずコンパイル不可
- **発見**: 2026-09-28 21:4x
- **症状**: `identifier idents no member "FComposition"` が 3 件
- **原因**: `strict private` はクラス自身のみ。同一ユニットの別クラス（`TPMLTextInputSystem`）からは見えない
- **対応**: 当該フィールドのみ `private`（ユニット内可視）へ移し、意図をコメントに明記
- **状態**: 修正済み（C-01）

### D-07 `strict protected` の `ContextRef` に他インスタンス経由でアクセスできない
- **発見**: 2026-09-28 21:5x
- **症状**: セッション生成時に親の `ContextRef` を読めない
- **原因**: `strict protected` の可視性規則。設計書 §4.1 は `Context` を public プロパティとしていた
- **対応**: `ContextRef` を public に変更（設計書の意図どおり）
- **状態**: 修正済み（C-01）

### D-08 CORBA インターフェースで保持したバックエンドの実体が解放されない
- **発見**: 2026-09-28 21:4x（設計時に自分で気付いた。実害が出る前に対処）
- **症状**: リーク（実測はしていない）
- **原因**: `{$interfaces corba}` により参照カウントが無いため、インターフェース変数を nil にしても実体は残る
- **対応**: `FBackendObject: TObject` を併せて保持し、`Destroy` で明示解放。理由をクラスのコメントに記載
- **状態**: 修正済み（C-01）

### D-19 生成された仮想メソッドと同名のプロパティを自前クラスに書いて衝突
- **発見**: 2026-09-28 22:4x（`PaPiMeLa.Video.Wayland.Types` の初回ビルド）
- **症状**: `Duplicate identifier "scale"`
- **原因**: `TPMLWaylandOutput` は生成された `Twl_output_listener` を継承し、仮想メソッド `scale` を override している。そこへ `property Scale` を足したため、同一クラス内で衝突した。**D-10 と同型の問題が、生成コードではなく自前の派生クラス側で再発した**
- **対応**: プロパティを `ScaleFactor` に改名し、理由をコメントに残した
- **状態**: 修正済み（C-01、T-05）
- **教訓**: 生成リスナーを継承する自前クラスでは、プロトコルのイベント名と同名のメンバを足せない。派生側にもこの制約が伝播する

### D-20 例外を握り潰す空の except ハンドラが 2 箇所
- **発見**: 2026-09-29（rawpaco の静的解析を導入し、初回実行で検出）
- **箇所**: `src/PaPiMeLa.TextInput.Fcitx.pas` の `Disconnect` と `Activate`
- **症状**: `on E: EPMLError do ;` で例外を黙って捨てていた。`RAWPACO-DEFENSE-001`（error 級）
- **原因**: どちらも「失敗しても処理を続けてよい」箇所だったため、意図的に無視していた。
  だが無視と握り潰しは別物で、後者は障害時に原因が追えなくなる
- **対応**: `FLastNonFatalError` フィールドに記録するようにした。抑制コメント
  （`// rawpaco:ignore`）は使っていない。`Activate` 側は「キーが消費されない」症状の
  直接の原因になりうる箇所（D-02 を参照）なので、記録が残る価値が高い
- **状態**: 修正済み（C-04）
- **備考**: **静的解析の導入で最初に見つかった実際の欠陥**。papimela 全体（手書き 4.5k 行、
  生成 9.2k 行、テスト・スパイク・ツール）で指摘はこの 2 件だけだった

### D-21 シートのリスナーを付ける前に capabilities が配送され、キーボードを取り出せない
- **発見**: 2026-09-29（`test/demo_japanese_input` を 5 秒動かしたら「キーマップ受信: False」だった）
- **症状**: `wl_seat` は束縛できているのにキーボードが一切動かない。`wl_keyboard.keymap` も
  `enter` も届かない
- **原因**: `TPMLWaylandConnection.Connect` がレジストリの roundtrip を 2 回行う間に
  `wl_seat.capabilities` が配送される。シートのリスナーを付けていたのはその**後**なので、
  capabilities を取りこぼし、`wl_seat_get_keyboard` を呼ぶ機会が無かった。
  **束縛とリスナー登録の間に dispatch を挟んではいけない**という Wayland の基本を外していた
- **対応**: 接続に `OnSeatBound` コールバックを追加し、レジストリハンドラが `wl_seat` を
  束縛した瞬間にシートオブジェクト（＝リスナー）を生成するようにした。ビデオバックエンドは
  `Connect` の前にこのコールバックを設定する
- **状態**: 修正済み（修正後は「キーマップ受信: True / フォーカス取得: True」）
- **教訓**: 静的解析もコンパイラも捕まえられない種類の不具合。**実際に動かしたから見つかった**。
  合成キーによる自動テスト（T-06）も通っていたので、対話デモを書かなければ残っていた


### D-22 ウィンドウのフォーカス変化が IME に伝わっていない
- **発見**: 2026-09-29（利用者が `test/demo_japanese_input` を実際に操作した出力から。
  「キーボードフォーカスを喪失 → 取得」が記録されているのに、IME 側へ何も送っていなかった）
- **症状**: 別のウィンドウへ移っても fcitx5 はこちらの入力コンテキストを注目したままになる。
  2 つのクライアントが同時に IME フォーカスを持つ状態になり、変換中テキストや
  入力モードがフォーカスをまたいで残る
- **原因**: `TPMLKeyboardState.SendFocus` は `WindowFocusGained` / `Lost` をキューへ積むだけで、
  IME へは何も通知していなかった。`FBackend.Activate` / `Deactivate` はセッションの
  `Start` / `Stop` でしか呼ばれていない
- **対応**: `IPMLKeyFilter` に `NotifyFocus` を追加し、`SendFocus` から呼ぶ。
  `TPMLTextInputSystem` はセッションのウィンドウと一致する変化だけを
  `Activate` / `Deactivate` へ中継する。`Start` / `Stop` と二重にならないよう
  `FFocused` で遷移のときだけ通す
- **状態**: 修正済み（実機検証 2026-09-29。T-07 を参照）
- **教訓**: 単一ウィンドウのデモでは症状が出にくい。**利用者が実際に触って別ウィンドウへ
  移ったログ**から見つかった。自動テストも対話デモも単一アプリしか見ていなかった

### D-23 サーフェスが解決できないときフォーカス喪失を取り落とす
- **発見**: 2026-09-29（D-22 の修正を実機で確かめる直前のコード読み）
- **症状**: `wl_keyboard.leave` で `user_data` からウィンドウ ID を引けなかった場合、
  `SendFocus(..., False)` を呼ばずに終わる。D-22 と同じ「IME がフォーカスを持ったまま」の
  状態が、別の入口から再現する
- **原因**: `HandleKeyLeave` が `WindowIDOf(ASurface)` の結果が 0 でないことを通知の条件に
  していた。サーフェスは `leave` の時点で既に破棄されていることがあり、そのとき 0 になる
- **対応**: 解決できなければ直前に保持していた `FKeyFocus` を使う。`FKeyFocus` は
  条件付きではなく必ず 0 に戻す。`leave` は「失った」という事実そのものなので、
  誰が失ったか分からなくても通知を落としてはいけない
- **状態**: 修正済み（実機検証 2026-09-29。別ウィンドウへの往復 4 回すべてで
  `フォーカスを喪失` と `取得` が対になって記録された）
- **教訓**: D-22 の修正で経路を作ったが、その経路に**通らない条件**が残っていた。
  修正が「送るようにした」で終わっていないか、送らない分岐が残っていないかを見る

### D-24 configure がウィンドウフラグ集合を丸ごと置き換え、生成時の指定が消えていた
- **発見**: 2026-09-29（pointer-constraints の実装中。`MouseGrab := True` のあと
  `TPMLWindowFlag.MouseGrabbed in Win.Flags` が False になり、テストが落ちた）
- **症状**: 最初の `xdg_toplevel.configure` が届いた時点で、`Resizable` や
  `Borderless`、`HighPixelDensity`、`MouseGrabbed` が `Flags` から消える。
  ウィンドウ自体は正しく振る舞う（バックエンドは生成時に設定済み）が、
  **アプリが `Flags` を見ると嘘の値が返る**
- **原因**: `TPMLWindow.ApplyFlags` が `FFlags := AFlags;` と集合を置き換えていた。
  バックエンドが報告するのは自分が知っている 3 つ（Maximized / Fullscreen /
  InputFocus）だけなので、それ以外は毎回消えていた
- **対応**: フラグごとに持ち主を決め、バックエンドが持つ集合だけを差し替える。
  `FFlags := (FFlags - BackendOwned) + (AFlags * BackendOwned)`。境界は定数
  `BackendOwned` としてコードに書き、「コンポジタしか知らないフラグ」と明示した
- **状態**: 修正済み（`test_pointer_constraints` が「configure のあとも生成時の
  Resizable が残る」を検査する）
- **教訓**: 新機能を足したときに**既存の嘘が露出した**類。`MouseGrabbed` を
  `Flags` に載せようとして初めて、同じ場所を通る `Resizable` も壊れていたと分かった。
  状態を 2 箇所が書くなら、どちらが持ち主かを型か定数で表に出す

### D-25 FPC の `Format` は `+` フラグを解釈しない
- **発見**: 2026-09-29（T-09 の出力が `rel=(313.1f, 313.1f)` になっていた）
- **症状**: `Format('rel=(%+.1f, %+.1f)', [X, Y])` が数値を出さず、`.1f` を文字として
  出力する。**表示される値が嘘になる**ので、デモの相対移動量は最初から読めていなかった
- **原因**: FPC の `Format` が受け付ける書式は `%[index:][-][width][.prec][type]` で、
  C の `printf` にある `+`（符号を必ず付ける）は含まれない。`%+` に当たると
  書式指定の解析が途中で止まる
- **実測**: `Format('(%+.1f)', [Single(1.25)])` → `(.1f)`。`%.1f` と `%6.1f` は正常
- **対応**: `+` を外して `%.1f` にした。負数には最初から `-` が付くので実害は無い
- **状態**: 修正済み
- **教訓**: C の書式をそのまま持ち込まない。**出力が壊れていることに気づけたのは、
  値が座標と一致しない（`rel` に `abs` の Y が出ていた）と分かったから**であって、
  形式だけ見ていたら見落としていた

### D-26 デモが絶対移動をすべて相対移動として数えていた
- **発見**: 2026-09-29（T-09 で拘束を一度も張っていないのに「相対移動 2960 件」と出た）
- **症状**: `demo_pointer_constraints` の集計が「絶対移動 0 件 / 相対移動 2960 件」。
  ロックを張れていないので相対移動は 0 件でなければならない
- **原因**: `XRel` / `YRel` が 0 かどうかで絶対・相対を区別していた。`SendMotion` は
  絶対移動でも前回位置との差を `XRel` / `YRel` に載せるので、この判定は常に「相対」になる
- **対応**: 要求側の状態（`Win.RelativeMouseMode`）で判断する。あわせて毎回 1 行出していた
  絶対移動を間引き、拘束の切り替えが埋もれないようにした
- **状態**: 修正済み（再実行で確認する）
- **教訓**: 検証のための道具そのものが嘘をついていた。D-25 と合わせて、
  **「テストが通った」ではなく「出た数字が辻褄に合うか」を見ないと気づけない**

### D-27 デモが小文字のキーシムしか受けず、Shift 付きで押すと無反応
- **発見**: 2026-09-29（T-09 の再実行。`（割り当ての無いキー keysym=$47）` が延々と出ていた）
- **症状**: `demo_pointer_constraints` で Shift を押しながら G / R を押すと何も起きない。
  $47 は大文字 `G`、$52 は大文字 `R` のキーシム
- **原因**: キーシムは大文字と小文字で別の値になる（`g` = $67、`G` = $47）。
  デモが小文字だけを見ていた。**操作説明を「G」「R」と大文字で書いていた**ので、
  そのとおりに Shift を押した利用者が無反応に遭った
- **対応**: `Ord('g'), Ord('G'):` のように両方を受ける。
  **定数 `KEY_g` / `KEY_G` を並べる案は Pascal が大文字小文字を区別しないため衝突する**
  （`Duplicate identifier`）。この衝突は D-09 / D-10 / D-11 / D-13 / D-19 と同型で 6 件目
- **状態**: 修正済み
- **教訓**: 指示の書き方が操作を誘導する。**大文字で書いたら大文字で押される。**
  診断行（割り当ての無いキーの keysym 出力）を入れておいたおかげで即座に分かった

### D-28 デモの状態行が相対移動のたびに再出力され、ログが埋まる
- **発見**: 2026-09-29（T-09 の再実行。「状態: ロック…」が数百行続いた）
- **症状**: 相対モード中、1 イベントごとに同じ状態行が出て、肝心の切り替えが埋もれる
- **原因**: 変化検知に使う文字列に相対移動の件数を含めていた。件数は毎イベント変わるので
  常に「変化した」と判定される
- **対応**: 状態の識別に使う文字列（種類・有効か・フォーカス）と、表示する文字列
  （件数を含む）を分けた
- **状態**: 修正済み
- **教訓**: 「前回と変わったら出す」の比較対象に、変わり続ける値を混ぜない

## B. 生成器 `wlscan-pas` の不具合（すべて修正済み）

いずれも **Pascal 固有**で、C では起こらない。wayland-scanner の移植で最も手間取った領域。

### D-09 オペコード定数と関数名が衝突
- **発見**: 2026-09-28 22:0x（生成ユニットの初回ビルド）
- **症状**: `overloaded identifier "WL_DISPLAY_SYNC" isn't a function` が多数
- **原因**: Pascal は大文字小文字を区別しないため、定数 `WL_DISPLAY_SYNC` と関数 `wl_display_sync` が同一識別子になる
- **対応**: オペコード定数に `_OPCODE` 接尾辞を付与（`WL_DISPLAY_SYNC_OPCODE`）
- **状態**: 修正済み（C-03）

### D-10 引数名が同一インターフェースのメソッド名と衝突
- **発見**: 2026-09-28 22:0x
- **症状**: `Duplicate identifier "axis"` が 4 件
- **原因**: `wl_pointer` はイベント `axis` を持ち、別のイベント `axis_stop` / `axis_discrete` / `axis_value120` / `axis_relative_direction` が引数 `axis` を持つ。クラス宣言内でメソッド名と同名の引数は許されない
- **対応**: インターフェース単位の予約名集合（全リクエスト名＋全イベント名）を作り、引数名が該当したら `_` を付与
- **状態**: 修正済み（C-03）

### D-11 引数名が型名を隠して可変長引数が関数呼び出しに解釈される
- **発見**: 2026-09-28 22:1x（21 プロトコル一括生成時）
- **症状**: `Syntax error, ")" expected but "(" found`（3 プロトコル）
- **原因**: `zwp_relative_pointer_manager_v1.get_relative_pointer` の引数名が `pointer` で、生成コード中の `Pointer(nil)` が変数 `pointer` の呼び出しと解釈された
- **対応**: 生成コードが使う型名（`Pointer`、`LongWord`、`wl_fixed_t` 等）も予約名として扱う
- **状態**: 修正済み（C-03）

### D-12 イベントを持たないプロトコルで空の `type` 節を出力
- **発見**: 2026-09-28 22:1x
- **症状**: `Syntax error, "identifier" expected but "PROCEDURE" found`（6 プロトコル）
- **原因**: リスナー宣言の前に無条件で `type` を出していた。イベントが 1 つも無いと中身が空になる
- **対応**: イベントを持つインターフェースが存在するときだけ `type` を出力
- **状態**: 修正済み（C-03）

### D-13 `Pwl_display` が生成ユニットと手書きユニットで二重定義
- **発見**: 2026-09-28 22:1x（設計時に気付いた）
- **原因**: `wl_display` は XML 上のインターフェースでもあり、手書きの `Platform.Wayland.Client` でも宣言していた
- **対応**: 生成器はコアプロトコルの `wl_display` について不透明型を出力しない（Client 側の宣言を使う）
- **状態**: 修正済み（C-03、T-04）

## C. 文書・判断の誤り（すべて訂正済み）

### D-14 「Wayland text-input-v3 に `preedit_styling` がある」と誤って説明した
- **発見**: 2026-09-28（IME 設計の相談中、プロトコル XML を確認して自ら誤りに気付いた）
- **症状**: 最初の回答で「text-input-v3 の `preedit_style` で範囲ごとのスタイルが取れる」と説明した
- **原因**: v1 / v2 の記憶に基づく誤り。v3 では `preedit_styling` が削除されており、`preedit_string` の引数は `text` / `cursor_begin` / `cursor_end` のみ（XML に "styling" は 0 回出現）
- **影響**: 大きい。誤ったままなら「Wayland 経路で文節が取れる」前提で設計してしまい、IBus / Fcitx 直結という**正しい結論に到達できなかった**

### D-15 設計書 §7.8 の文節状態マッピング規則が変換前のかなを誤判定
- **発見**: 2026-09-28 21:4x（Fcitx バックエンドの実測時）
- **症状**: 「`Underline` のみ → `Converted`」という規則だと、ローマ字入力中の「わたしのなまえ」（`Underline` 単独で届く）を**変換済みとして描いてしまう**
- **原因**: 設計書執筆時に実機のフラグを観測していなかった（当時は `[要検証]` と明記されていた）
- **対応**: 「`HighLight` がどの文節にも無ければ全文節を `Unconverted`」という条件を追加。実装と設計書の両方を修正し、テスト T-03 が変換前 14 回すべて「未変換」になることを検証
- **状態**: 修正済み（T-03）

### D-16 設計書 §7.2 が Fcitx5 の位置単位を一律「文字単位」と記載
- **発見**: 2026-09-28 21:4x（実測時）

### D-17 生成ファイルの文字化けを誤診し、根拠のないコメントを書いた
- **発見**: 2026-09-28 22:1x
- **症状**: `grep` が生成ファイル内の識別子を見つけられず、`file(1)` が "NEL line terminators" と報告したため、`TStringList.SaveToFile` が UTF-8 を壊していると判断した
- **実際**: **ファイルは最初から正しかった**。`grep` がロケールの都合で多バイト文字を含むファイルを扱えていなかっただけで、`LC_ALL=C grep -a` では全て正常に一致した
- **影響**: 出力方式を `TFileStream` のバイト直書きに変更した（無害で、むしろ明示的なので残した）。ただし**「TStrings がコードページ変換で UTF-8 を壊す」という誤った説明をコード内コメントに書いた**
- **対応**: コメントを事実に即した記述へ訂正。誤った断定をコードに残さないこと自体を教訓として記録
- **状態**: 訂正済み

### D-18 `SDL_ibus.c:115` の型名検証が常に成功する
- **発見**: 2026-09-28（SDL のアーキテクチャ評価中）
- **箇所**: `reference/SDL/src/core/linux/SDL_ibus.c` 115 行目

- **状態**: **未対応・報告しない方針**。SDL は AI 生成物の貢献を受け付けないと明示しているため、PR も Issue も出さない。報告する場合はプロジェクト所有者が自分の言葉で行う
- **教訓**: 「C コードを無検証で写してはならない」の実例として `docs/CODING-STYLE.md` §3 に記載した
